## 1. 产品概述

**一句话定位**：基于 Monad 的链上可信抽奖平台 —— 用智能合约托管 + 可验证随机数，彻底消除抽奖场景中"主办方作弊"的信任问题。

**解决的问题**：传统抽奖（线上活动、线下活动、社区营销）中，参与者无法验证三件事：
1. 中奖名单是不是真的（没中奖的人是真的参与了吗？）
2. 开奖过程是不是被操纵的（主办方想给谁就给谁？）
3. 承诺的奖品真的会发吗？

本产品把这三件事全部变成**链上可验证**：资格名单在链上、随机数可验证、派奖由合约执行。

## 2. 核心机制（用户旅程）

```
参与者                                  合约                       主办方/赞助方
   │                                     │                             │
   │  ① register() + 10 MOD 押金          │                             │
   ├────────────────────────────────────>│ 资格名单 +1，押金入托管       │
   │                                     │                             │  ② fundPrizePool() 注入奖金
   │  ③ 等待锁仓期（默认 3 天）            │ 押金锁定，不可取回           │
   │                                     │                             │
   │  ④ 到期后任何人触发 draw(userSeed)   │                             │
   ├────────────────────────────────────>│ 请求 Pyth Entropy            │
   │                                     │ <── 随机数回调 ──            │
   │  ⑤ 链上公布 N 名中奖者               │ 随机数洗牌取前 N 名（均分）    │
   │                                     │                             │
   │  ⑥ claimDeposit() 领回 10 MOD        │ 中奖者们各领 奖池/N（均分）    │
   │  （未中奖押金 100% 退回）             │                             │
```

关键设计决策（已拷问确认）：

| 决策点 | 结论 | 理由 |
|--------|------|------|
| 资格验证 | **押金托管进合约**，锁仓 3 天（参数化） | 完全链上可验证、天然防女巫、无链下信任假设，详见 [ADR 0001](./adr/0001-escrow-qualification.md) |
| 参与登记 | **链上注册交易**（`register()` 附带押金），不支持网页填地址 | 一笔交易同时完成所有权证明 + 托管 + 上名单 |
| 防女巫 | 一地址 = 一份押金 = 一次资格 | 押金有真实成本，刷号经济上不划算 |
| 随机数 | **Pyth Entropy VRF**（Monad testnet 已部署） | 可验证公平，且支持请求方自带种子 |
| 开奖触发 | **任何人可触发**（Permissionless），条件：到期 + 名单非空 | 无需信任项目方；Monad gas 便宜，触发成本可忽略 |
| 奖池 | **赞助方单独注入**，与押金严格分离 | 押金是资格凭证不是门票，开奖后 100% 退回 |
| 中奖人数与派奖 | **winnerCount 部署参数（默认 1）**，多名中奖者**均分奖池**（开奖时刻快照 ÷ N） | 均分叙事最"公平"、链上可验算；名次/权重分配列入未来规划 |
| 中途取回 | **锁仓期内禁止**，合约不提供取回函数 | "维持 3 天任务"定义清晰；pull 模式领回 |

## 3. 两种开奖形式

### 3.1 定时开奖
- 部署合约时设定 `drawTime` 与 `lockPeriod`（默认 3 天）。
- 到期后任何人可调用 `draw(userSeed)` 触发，`userSeed` 由项目方预先公布（如写在活动页面上），公开承诺、不可抵赖。
- 场景：线上社区活动、周期性营销抽奖。

### 3.2 现场开奖（差异化亮点）
- 现场观众**扫码**打开参与页面，各自产生随机数（输入/摇手机）。
- 前端将所有观众熵 hash 合并为 `userSeed`，由现场任意一名持钱包者（或主持人钱包）发起 `draw(userSeed)` 交易。
- Pyth 验证者熵与现场熵混合 → **"把现场变成随机数源"**，观众真实参与了开奖过程。
- 场景：黑客松颁奖、线下 meetup、展会抽奖。

两种形式共用同一随机数链路（Pyth Entropy），合约逻辑完全一致，仅 `userSeed` 来源不同。

### 3.3 线下活动准入：防远程薅羊毛（详见 [ADR 0002](./adr/0002-on-site-admission-signature.md)）

**威胁**：`register()` 若完全无许可，全球任何地址（testnet 押金零成本）都能入围，线下活动定向的赞助奖池会被远程羊毛党稀释——奖金 > 押金时薅羊毛是正期望收益。

**方案：签发者准入签名（同合约双模式）**

```
参与者到场 → 签到处核验门票/胸牌（物理在场）
          → 工作人员工具页对参与者地址 ECDSA 签名（绑定地址+活动ID+有效期）
          → 生成二维码回传给参与者
          → 参与者扫码，自行发起 register(sig) + 10 MOD 押金
          → 合约 ecrecover 验签通过 → 入围
```

- **合约层**：构造函数接收 `issuer` 地址。非零 = 线下模式（注册验签），零地址 = 线上无许可模式。一套代码，两种产品形态。
- **威胁缓解对照**：

| 攻击手法 | 缓解 |
|----------|------|
| 远程直接 register() | 验签失败，交易回滚 |
| 窃取/转发他人签名 | 签名绑定被签地址，对其他地址无效 |
| 现场公布统一口令 | 不使用口令；签名不经过公开信道（二维码当面回传） |
| 工作人员给场外朋友签名 | 有界信任：与现实中检票员放熟人进场同级；签名记录链上可事后审计 |
| 一人多钱包刷票 | 签到处人工核验"一人一签"，合约层不做限制 |
| 签发者密钥泄露 | 密钥无提款权限，最大损失 = 若干张无效准入票；作废活动重启即可 |

**残余信任声明**：线下模式的准入信任 = 线下活动本就存在的检票环节，未新增信任假设；签发者无法触碰押金与奖池。

## 4. 随机数设计

- 服务：**Pyth Entropy**（Monad testnet，V2 接口）。
  > ✅ 勘误更新（2026-09-05 实测确认）：真实入口为 ERC-1967 代理 `0x825C0390f379C631F3CF11a82a37d20bddf93C07`（默认 provider `0x6CC1...6344`，请求费实测 0.128 MON，回调 `entropyCallback`）；原文地址 `0x3682...e320` 已证伪（仅治理函数），回调名 `providerConfirmedRandomNumber` 系笔误。详见 [tech-design.md §4](./tech-design.md)。
- 流程：`draw(userSeed)` → 合约调用 Entropy `requestV2`（附带 userSeed，缴纳请求费）→ Pyth 验证者回调 `entropyCallback` → 合约以随机数为种子对名单做部分洗牌（Fisher-Yates），取前 N 名为中奖者。
- 公平性：随机数 = 验证者熵 + 用户种子共同决定，任何单方（项目方、验证者、观众）都无法独立操纵结果，且过程链上可审计；洗牌确定性可复现，任何人可按同一随机数在链下重算中奖名单核验。
- 请求费：触发者垫付，开奖成功后从奖池中返还（金额极小）；**奖池不足时跳过返还（触发者自担）**——回调永不 revert，保证开奖不因退款卡死。

## 5. 信任模型对比（评委核心关注）

| 信任风险 | 传统抽奖 | Monad Blitz |
|----------|----------|-------------|
| 参与者真实性 | 名单不透明，可凭空造假 | 链上注册事件，一地址一份押金 |
| 主办方操纵结果 | 黑箱开奖，无法验证 | Pyth Entropy 可验证随机数，任何单方无法操纵 |
| 奖品承诺 | 口头发钱，可能赖账 | 奖金预先锁入合约，合约强制派发 |
| 押金安全 | 无此概念 | 合约托管，到期 100% 退回，锁仓期内谁也拿不走 |
| 开奖执行 | 主办方说了算 | 到期后任何人可触发，无准入 |

**残余信任假设**（诚实声明）：Pyth 验证者网络（多数诚实）、Monad 共识层；线下活动模式另含签发者准入信任（与检票同级，无资金权限，见 3.3 节）。除此之外无项目方特权（合约无 owner 提款函数，仅保留参数设置在部署时固定）。

## 6. 合约设计草案（Lottery.sol）

```
状态
  participants: address[]          // 注册名单（有序，用于随机索引）
  registered: mapping(addr => bool)
  drawTime / depositAmount / winnerCount   // 部署时固定参数（issuer/entropyTimeout 见技术方案）
  status: Open → Drawing → Drawn
  winners: address[]               // N 名中奖者，实际人数 = min(winnerCount, 参与人数)
  prizePool: uint256               // 赞助方注入，与押金分离

核心函数
  register(bytes admissionSig)     // msg.value == 10 MOD，push 名单
                                   // 线下模式（issuer != 0）须验签；线上模式签名可空
  submitEntropy(bytes32 e)         // 现场观众提交熵，聚合为熵根（见 tech-design §2.4）
  draw(bytes32 userSeed)           // require 到期 + 名单非空 + 未开奖；请求 Entropy
  entropyCallback(...)             // VRF 回调：以随机数为种子部分洗牌选 N 名，状态 → Drawn
                                   // 快照奖池，prizePerWinner = 快照 ÷ 实际中奖人数
  claimDeposit()                   // 开奖后，参与者领回 10 MOD（pull 模式）
  claimPrize()                     // 每名中奖者领 prizePerWinner（均分，pull 模式）
  fundPrizePool() payable          // 赞助方注入奖金（仅 Open/Drawing，Drawn 后拒绝）

构造参数
  issuer = address(0)              // 线上活动：无许可注册
  issuer = 0xAAA...（主办方密钥）   // 线下活动：注册须附签发者准入签名
  winnerCount = N                  // 中奖人数（默认 1），均分奖池

事件
  Registered(addr) / DrawRequested(seq, userSeed) /
  WinnersSelected(winners[], random) / DepositClaimed(addr) / PrizeClaimed(addr)
```

要点：押金账本与奖池账本分离核算；无 owner 提款函数；锁仓期内无任何取回路径；派奖以开奖时刻快照均分，Drawn 后奖池不再接受追加（防资金滞留）。

**主办方创建流程（/create 页）**：主办方连接钱包 → 表单配置（准入模式 / 押金额 / 开奖时间 / 中奖人数）→ 浏览器内直接部署合约，无需命令行 → 得到带 `?addr=` 的活动链接分享给参与者。

## 7. 边界情形与风险清单（拷问产出）

| # | 风险/边界 | 应对 |
|---|-----------|------|
| 1 | **Monad 10 MON 底金规则与押金冲突**：账户余额过低的用户存入 10 MOD 后，交易可能因 ending balance 低于底金而回滚（除非触发 emptying exception） | **已结（2026-09-05 规则推演）**：12 MOD 账户 register 必回滚——期末余额 ≈2 MOD < min(期初 12, 10)=10，且 emptying exception 仅适用于"清空交易"（注册不清空账户，不适用）；**参与门槛 = 余额 ≥ 20 MOD + gas（建议 21 MOD）**；7702 委托账户无 emptying exception，同按此门槛。13:00 开发阶段冒烟：20 MOD 成功用例 + 12 MOD 失败用例各一。<br>**降押金分析**（2026-09-05 追问）：押金降为 1 MOD 只把门槛降到 ≈11 MOD，**不消除规则**——期初余额 <10 MOD 的账户押 1 MOD 同样回滚（floor = min(期初, 10)）。**决策：维持 10 MOD**（叙事一致 + 演示钱包 ≥21 MOD 无碍；testnet 押金零成本，防女巫真实成本来自锁仓而非金额），正式部署可经 `depositAmount` 参数按需调低 |
| 2 | Pyth Entropy 回调失败/延迟 | draw 状态机允许在超时后重新 `draw()` 请求（重新缴费 ≈0.128 MON/次），随机数未产生前状态保持 Drawing。⚠️ testnet 入口历史仅 ~1 笔请求，**13:00 冒烟必须先跑一次完整 requestV2→回调链路**再定演示方案；若 keeper 失联，备选 = 主网部署（1.4 MON/次）或降级 blockhash |
| 3 | 名单为空时到期 | draw() revert，任何人可在有新注册后再触发；赞助方奖金不受影响 |
| 4 | 中奖者/参与者永不领回 | 资金安全留在合约中可随时 claim（pull 模式无资金损失），多期化后在后续版本增加超时回收 |
| 5 | 低余额账户交易频率限制（<10 MON 每 3 区块 1 笔） | 对本产品无实质影响，注册/领回均为单笔操作 |
| 6 | 演示等待不了 3 天 | `lockPeriod`/`drawTime` 为部署参数，演示合约设为分钟级；正式使用设为 3 天 |

## 9. 评委关注点映射

- **创新性**：观众扫码集熵参与开奖，把线下场景变成链上随机数源（非套壳 VRF demo）。
- **技术难度**：Monad 原生部署 + Pyth Entropy 异步回调集成 + 押金/奖池双账本 + 主办方浏览器内一键部署创建活动。
- **Monad 特性利用**：低 gas 使"任何人可触发开奖"经济可行（以太坊上触发费高得多）；高 TPS 支撑现场大量观众同时扫码注册。
- **商业潜力**：活动营销、社区运营、展会互动的通用信任基础设施；商业模式与 Web3 关联性论证详见第 10 节。

## 10. 商业价值与 Web3 关联性

### 10.1 为什么抽奖场景必须是 Web3（关联性论证）

抽奖信任问题的根因是**发起方与参与者之间的信息不对称**：名单、开奖过程、资金去向全部是发起方的私有数据，参与者只能选择"信或不信"。Web3 在这里不是加分项，而是该问题的**唯一结构性解法** —— 把三个环节全部搬到公开可验证的账本上，信任从"信任平台品牌"降级为"验证数学与代码"：

| 抽奖环节 | Web3 组件 | 消除的信任假设 |
|----------|-----------|----------------|
| 谁参与了 | 链上注册事件（公开账本 + 押金托管） | 名单造假、机器人刷量 |
| 谁中奖了 | Pyth Entropy 可验证随机数 | 开奖操纵、暗箱操作 |
| 钱去哪了 | 合约托管奖池、合约强制派发、押金到期可验退回 | 赖账、挪用奖金 |

**反向论证 —— Web2 为什么做不了**：
- 中心化抽奖平台（问卷抽奖、小程序抽奖）的数据库可被运营方随时篡改，"后台透明化截图"毫无证明力；
- 引入第三方公证只是**信任转移**（从平台转移到公证方），且线下公证成本高、周期长；
- Web3 方案把"公证"变成协议内置属性，边际成本 ≈ 一笔 VRF 请求费 + 亚美分 gas。

**Monad 让商业模型成立（选链的根本原因）**：
- 以太坊主网一笔注册交易 gas 可达数美元，高于多数抽奖活动的人均价值，链上抽奖**经济上不成立**；
- Monad 的亚美分 gas 使"10 MOD 小额押金 + 任何人可触发开奖（触发费可忽略）"成为可能；
- 高 TPS 支撑现场百人级**并发扫码注册**（传统链会拥堵掉单）；
- Monad 原生生态（Pyth Entropy 已部署 testnet）让集成成本降到黑客松一天可完成的量级。

### 10.2 目标客户与付费场景

| 客户群 | 典型场景 | 核心付费动机 |
|--------|----------|--------------|
| 品牌 / 市场部门 | 新品发布、转发抽奖升级为链上抽奖 | "公平可验证"成为品牌信任资产，tx hash 可作为营销素材二次传播 |
| Web3 项目方 / DAO | 社区活动、AMA、持仓者回馈 | 天然链上用户，防女巫（一地址一押金）让预算精准触达真人 |
| 线下活动主办方 | 展会、黑客松、meetup 颁奖 | 观众扫码集熵参与开奖 = 现场互动工具，兼得仪式感与公信力 |
| 直播 / 内容平台 | 弹幕抽奖、礼物抽奖 | 主播自证清白，平台减少"内定"舆情 |

### 10.3 收入模式（可持续性路径）

1. **按场次 SaaS 服务费**：主办方创建活动时支付小额服务费（testnet 免费、mainnet 收费），当前 MVP 的 `fundPrizePool` 流程未来加一层活动工厂合约即可承载；
2. **门票分成**：未来规划中的门票模式（押金退回 + 小额 ticket 进奖池）按比例分成，是社区运营场景的自然延伸；
3. **增值服务**：定制开奖大屏 UI、现场集熵互动包、活动数据报告（链上数据天然结构化）。

商业模式的关键自洽点：**押金与奖池 100% 归用户与中奖者，平台收入来自服务费** —— 收入结构本身不与参与者利益冲突，这是"可信"人设的商业化底线，写进产品原则。

### 10.4 生态价值与壁垒

- **对 Monad 生态**：每场活动都是链上真实使用——参与者被引导装钱包、领水、完成人生第一笔链上押金与领回，是低门槛的用户获取漏斗（黑客松"生态贡献"评分点）；
- **壁垒判断**：合约本身轻且开源、无技术垄断；壁垒在于**场景运营先发**（活动模板、签发工具、集熵互动的产品化打磨）与 Monad 原生身份（成为 Monad 社区活动的默认抽奖基础设施）。
